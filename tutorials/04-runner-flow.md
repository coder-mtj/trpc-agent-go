# 04 · Runner 主流程详解：用户说一句话后，内部发生了什么

> 阅读目标：跟着 `runner.Run(...)` 的代码，把一次对话的完整内部流程走一遍。
> 代码位置：`trpc-agent-go/runner/runner.go`

---

## 1. 开场：Run 是唯一入口

用户每说一句话，程序都会调用：

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 唯一入口：用户每说一句话，程序都会调用它
events, err := runner.Run(
    ctx,                                            // 上下文（随身记事本）
    "user-001",                                     // 用户 ID
    "session-001",                                  // 会话 ID
    userMessage("Calculate what 2+3 equals"),       // 用户说了什么
)
```

`Run` 方法内部是一条清晰的流水线。我把它拆成 **10 步**，每一步对应代码里的一段。

> 小提示：代码里有很多"计时 span"（`startRunnerLatencySpan`），那是用来记录每一步耗时的监控埋点，可以忽略不看。

---

## 2. 第 1 步：准备工作（生成"工单号"）

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 每次 Run 都生成一个唯一的 RequestID（类似快递单号）
ro := &runner.RunOptions{
    RequestID: uuid.NewString(),
}
```

每次 Run 都会生成一个唯一的 `RequestID`（类似快递单号）。后面所有事件、日志、追踪都靠它关联起来。

如果调用方传了额外选项（比如 AppName、ExecutionTrace 开关），也会在这里合并。

---

## 3. 第 2 步：创建"执行上下文"（context）

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 给本次运行创建独立的上下文（相当于"随身记事本"）
// 用户中途取消时，整个任务链都会收到取消信号
execCtx := r.newExecutionContext(ro)
```

Go 程序里，`context.Context` 是"贯穿整个任务的随身记事本"：任务取消信号、超时、请求 ID 等都会放在里面传递。这一步给本次运行创建了独立的上下文——**如果用户中途取消，整个任务链都会收到取消信号**。

---

## 4. 第 3 步：取/建会话（Session）

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 用三个维度定位一场对话：应用 + 用户 + 会话
sessionKey := map[string]string{
    "app_name":   effectiveAppName,   // 应用名（比如 calculator-app）
    "user_id":    userID,             // 用户 ID（user-001）
    "session_id": sessionID,          // 会话 ID（session-001）
}

// 存在就取出来（带着历史继续聊），不存在就新建一个空会话
sess, err := r.getOrCreateSession(sessionKey)
```

框架用三个维度定位一场对话：**应用 + 用户 + 会话**。

- 如果这场对话已经存在 → 取出来（继续聊，带着历史）；
- 如果不存在 → 创建一个新的空会话。

大白话：店长翻开点单记录本，找到这一桌的旧记录；没有就开一本新的。

---

## 5. 第 4 步：检查"是否要从上次停下的地方继续"

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 检查上次是否停在"等用户回答"的地方
// 如果是，就记下"该继续跑的智能体"，用于下一步
ro, awaitUserReplyRootName, err := r.applyAwaitUserReplyRoute(...)
```

有时候智能体会主动说"我需要你回答一个问题才能继续"。它会留下一个"路由标记"，告诉 Runner：**等用户回答后，回到我这个智能体继续跑**。

这一步就是检查这个标记。如果上次确实停在这里，就把"该继续跑的智能体"记下来，用于下一步。

大白话：上次服务员问了你"要辣还是微辣？"，你回答了，这一步就是让同一个服务员接着处理你的回答。

---

## 6. 第 5 步：选择要跑的智能体（Agent）

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 根据规则（调用方指定 / 继续路由 / 候选选择器）选一个智能体接单
ag, err := r.selectAgentForRun(ro)
```

一个 Runner 可以注册多个智能体。这一步根据：

1. 调用方有没有指定智能体名字；
2. 第 4 步的"继续路由"；
3. 有没有配置"候选选择器"（比如根据用户意图自动选一个最合适的智能体）；

最终确定这次由哪个智能体"接单"。

---

## 7. 第 6 步：整理要发给模型的消息

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 消息预处理：如果配置了"用户消息改写器"，就在这里改写
// 没有配置就直接用用户的原话
invocationMessage, err := r.resolveCurrentTurnMessages(...)
```

这一步做"消息预处理"：如果配置了 `UserMessageRewriter`（用户消息改写器，比如把用户说的口语整理成规范指令），就在这里改写。

正常情况下没有配置的话，就直接用用户的原话。

---

## 8. 第 7 步：生成"工单"（Invocation）并登记

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// Invocation 是本次任务的完整工单：装着会话、消息、智能体、运行选项
invocation := r.newRunInvocation(sess, invocationMessage, ag, ro)
```

`Invocation` 是**本次任务的完整工单**：装着会话、消息、智能体、运行选项。它会挂在 context 上，后续所有组件（包括工具）都能通过它拿到上下文。

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 把工单登记到"正在运行的任务表"里
// 登记后，外部就能通过 RequestID 查询/取消这次运行
handle := r.registerRun(ro.RequestID, &RunStatus{...}, queuedUserMessages)
```

然后把这个工单登记到"正在运行的任务表"里（`registerRun`）。登记后，外部就能通过 RequestID 查询/取消这次运行。

---

## 9. 第 8 步：把用户消息存进会话

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 在智能体开工之前，先把用户这句话存进会话档案
// 这样即使后面运行失败，用户说的话也不会丢
r.persistCurrentTurnMessages(currentTurnSession, invocation, ag)
```

在让智能体开始干活**之前**，先把用户这句话存进会话档案。这样即使后面运行失败，用户说的话也不会丢。

这一步还会做"历史播种"（seed）：如果这场对话是第一次，可能把预设的系统消息（比如"你是 XX 助手"）一起存进去。

---

## 10. 第 9 步：给工单"装上配件"，然后启动智能体

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

// 给工单"装配件"：
attachSessionAppender(invocation, sess)   // 事件自动追加到会话（边干边记录）
attachFlusher(invocation)                 // 强制保存通道，需要时立刻写进存储
attachLivesession(invocation, sess)       // 让工具/子智能体能拿到"当前会话"
enableBarrier(invocation)                 // 同步屏障，保证操作按顺序执行

// 启动智能体（带插件），它产生的所有事件从这条"事件流"里流出来
agentEventStream := agent.RunWithPlugins(invocation, ag)
```

这几行是"装配件"：

| 配件 | 作用（大白话） |
|------|----------------|
| `appender` | 智能体产生的每个事件，自动追加到会话档案里（边干边记录） |
| `flusher` | 一个"强制保存"通道，某些时刻需要立刻把数据写进存储 |
| `livesession` | 让工具/子智能体能拿到"当前正在用的会话" |
| `barrier` | 同步屏障，保证某些操作按顺序执行 |

装好后，调用 `agent.RunWithPlugins`：

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

func runWithPlugins(invocation *agent.Invocation, ag agent.Agent) (<-chan *event.Event, error) {
    // 带插件地启动智能体
    runPluginsBefore()   // 先跑"前置插件"（guardrail 安全检查等）
    events := ag.Run(invocation)   // 再跑智能体本身
    runPluginsAfter()    // 再跑"后置插件"
    return events, nil   // 返回事件流
}
```

插件系统在这里生效：**在智能体开工前和收工后，插件都有机会"插一脚"**（比如安全护栏检查消息、身份校验）。

智能体一开工，就开始产生事件，源源不断地从 `agentEventCh` 通道里流出来。

---

## 11. 第 10 步：转发事件流（processAgentEvents）

```go
// 概念版伪代码：用 Go 语法演示逻辑，真实项目就是 Go 实现

return r.processAgentEvents(
    sess, invocation,
    agentEventStream,   // 智能体产生的事件
    handle,             // 运行登记句柄
)
```

这是**最后的对外出口**。`processAgentEvents` 做的事：

1. 从智能体事件通道里逐个收事件；
2. 把事件**追加进会话档案**（这样历史记录完整）；
3. 把事件**转发给你**（通过返回值 `events` 通道）；
4. 遇到"强制保存"请求时，把数据写入存储；
5. 运行结束后清理登记。

你的程序拿到 `events` 通道后 `for range` 逐个处理，这就是上一篇看到的代码。

## 12. 一张完整的流程图

```
用户说了一句话
   │
   ▼
┌─ 1. 生成 RequestID（快递单号）─────────────────┐
┌─ 2. 创建执行上下文（任务取消信号）──────────────┤
┌─ 3. 按 (应用, 用户, 会话) 取/建 Session ────────┤
┌─ 4. 检查"是否继续上次停下的智能体" ─────────────┤
┌─ 5. 选一个 Agent（智能体）─────────────────────┤
┌─ 6. 整理要发给模型的消息 ──────────────────────┤
┌─ 7. 生成 Invocation（工单）并登记运行 ──────────┤
┌─ 8. 把用户消息存进会话 ────────────────────────┤
┌─ 9. 装配件 → agent.RunWithPlugins 启动智能体 ──┤
┌─ 10. processAgentEvents 转发事件给你 ──────────┘
   │
   ▼
你收到事件流，逐个处理（打印、存库、触发业务...）
```

---

## 13. 两个值得注意的设计

### 设计一：先保存，再执行

第 8 步在智能体开工**前**就把用户消息存进会话。好处是：哪怕模型调用失败、网络中断，用户的输入也已经安全落库，不会丢。

### 设计二：事件边产生边记录边转发

第 9、10 步里，智能体每产生一个事件，`appender` 就把它写进会话，同时转发给你。这就是"流式"体验的来源——不用等全部结束，实时就能看到进展。

---

## 14. 小结

`runner.Run` 的 10 步可以浓缩成三句话：

1. **定位**：找到或创建这场对话（Session），选好智能体（Agent）；
2. **准备**：生成工单（Invocation）、保存用户消息、装好配件；
3. **执行与输出**：启动智能体，把产生的事件一边存档案、一边转发给你。

下一篇，我们讲"工具系统"——智能体是怎么"动手"的，以及工具安全是怎么管的。
